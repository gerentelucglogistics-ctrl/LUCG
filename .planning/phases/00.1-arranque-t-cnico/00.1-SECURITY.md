Tipos de evidencia usados en la columna Mitigación:

## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| agente → shell / GitHub / paneles | El agente corre en bypassPermissions; el hook `guardia-prod.sh` y el deny de `settings.json` son la barrera técnica hacia prod y main | Comandos con poder de despliegue; tokens del llavero |
| repo y Actions → público | Repo público (D-19): archivos, logs y artefactos de Actions los descarga cualquier usuario de GitHub | Código, evidencia, reportes de Playwright |
| Internet → Supabase pooler / Auth | Pooler y Auth públicos | Contraseñas de roles, credenciales de usuarios, JWT |
| navegador → API | Bearer JWT no confiable hasta validarlo; contexto de RLS por transacción | JWT (ES256/RS256), datos de cuenta |
| API / PWA / consola → Sentry | Errores salen a un tercero (habeas data) | Trazas, cabeceras filtradas |
| CI → dominios protegidos de Vercel | Secretos de bypass por proyecto | VERCEL_BYPASS_SITE/WEB/DRIVER |
| PR (incluidos forks) → GitHub Actions | Código no confiable con acceso potencial a secretos | Secretos de repo y de entornos |
| humano → main / prod | Única vía hacia producción (PR dev→main, revisor del entorno prod) | Despliegue a prod |

## Riesgos residuales (fase 0.1.1)

Quedan por escrito, no resueltos. Detalle y consecuencias en ADR-009.

- **R1** la guardia no ve código ejecutado desde archivos ni otros lenguajes; no es frontera de seguridad.
- **R2** el token admin `github-lucg` (D-04) sigue legible por la sesión del agente y con él se podría, fuera de la guardia, volver a poner revisores en prod, activar `can_admins_bypass`, cambiar el ruleset o fusionar a main: esa vía la cierra solo la guardia, no el diseño de GitHub.
- **R3** Vercel publica el front de prod al fusionar a main sin la aprobación (diferido en CONTEXT).
- **R4** las capturas PNG no las revisa la compuerta.
- **R5** los secretos de Actions a nivel de repo `VERCEL_TOKEN` y `VERCEL_BYPASS_*` no están atados al entorno prod y el token del bot tiene el scope `workflow`: un workflow nuevo o modificado en un PR del bot podría usar `VERCEL_TOKEN` para publicar el front de prod sin la aprobación de `jaras97`. Mitigación parcial: el PR pasa por CI y el desarrollador revisa el PR dev→main; mover `VERCEL_TOKEN` al entorno prod queda fuera de esta fase.
- **R6** dev no exige revisiones, así que un PR del bot que debilite la guardia y su prueba a la vez pasa el check `guardia` y se fusiona en dev (peor caso: dev, ADR-008; prod sigue con la aprobación de `jaras97` y el desarrollador ve el cambio en el PR dev→main).
- **R7** el token de `jaras97` sigue legible en el llavero del mismo usuario de macOS (D-02a enmendada); con él se podría aprobar prod. Lo mitiga solo la guardia (bloquea `pending_deployments`, `environments/prod` y volcados del llavero); cierre definitivo: correr el agente en un usuario de macOS sin esas credenciales. Evidencia observada: en el plan 05 un ejecutor intentó volcar el llavero y la guardia lo bloqueó, lo que confirma que R7 es real y que la guardia funciona como barrera.

Nota: el resultado A6 del plan 01 fue 200: el bot puede alcanzar los endpoints de secretos del repo y del entorno prod; la guardia es la barrera para `gh secret`.

Variables de repo creadas en el plan 05: `E2E_SUPABASE_URL` y `E2E_SUPABASE_PUBLISHABLE_KEY` (valores públicos de dev, sin secretos).

## Nota sobre D-17 (`prevent_self_review`)

El entorno `prod` queda con `prevent_self_review: false`. Pitfall 9: los PR dev→main (#3, #8) y las aprobaciones de `deploy-prod` los hizo `gerentelucglogistics-ctrl`; con revisor único `jaras97`, `prevent_self_review` no bloquearía al desarrollador mientras fusione con la cuenta LUCG, y lo único que haría es impedir que la misma cuenta apruebe lo que ella misma lanzó. D-17 deja libre fusionar con cualquiera; el riesgo de autoaprobación del agente lo cierran D-01, D-02 y D-05 (el bot no es revisor), con R7 como residual.
