## Summary

El esqueleto existe pero **nunca ha funcionado de punta a punta**. Los primeros workflows en `dev` (2026-11-26 18:43) fallaron. CI cayó en `ruff check` y el despliegue cayó porque `vars.SUPABASE_PROJECT_REF` está vacía. El preview de Vercel para `dev` también falló, muy probablemente porque el Root Directory sigue en la raíz. Al correr las herramientas en local salió esto: los builds de site, web y driver pasan; `pnpm -r typecheck` pasa; `pnpm lint` falla porque web y driver no tienen `eslint.config.js`; la API tiene 11 errores de ruff, 4 archivos sin formato y 1 error de mypy; `pytest` falla sin base. No hay `supabase/config.toml`, así que `supabase start` y `supabase db reset` no pueden correr en CI. No hay `apps/api/uv.lock`. Los íconos de la PWA no existen.

Desde que se escribió el kit cambiaron tres proveedores y eso rompe los pipelines escritos. (1) **Supabase CLI v3** salió el 2026-11-02 y `supabase/setup-cli` instala `latest` (v3.4.0). En v3 los comandos de base apuntan a la base local salvo que se pase `--remote`, y los cambios en proyectos alojados piden `--yes`. Por eso `migrate.yml` tal como está **migraría la base local del runner** y no Supabase dev. (2) **sentry-sdk 3.0** quitó `send_default_pii` y recoge cuerpos HTTP, datos de usuario y variables de los frames por defecto. Esto pesa por habeas data. (3) La **Deployment Protection estándar de Vercel** protege todo lo que no sea dominio de producción, y `dev.`, `app-dev.` y `repartidor-dev.` son dominios de rama de preview. Sin el secreto de bypass para automatización, el humo con curl y Playwright reciben 401.

Hay dos trampas de secuencia de GitHub que el plan tiene que resolver primero. Los eventos `schedule`, `workflow_run` y `workflow_dispatch` solo usan workflows que estén en la **rama por defecto**, y hoy esa rama es `main`, que todavía es el sitio viejo. Mientras no cambie, `e2e-dev.yml` nunca se dispara tras el despliegue a dev, el cron de D-08 no corre y `migrate.yml` no se puede lanzar a mano. Además, el repo está en una cuenta personal y es **público**, y el usuario del agente (`jaras97`) no puede configurar la protección de ramas porque solo tiene WRITE.

**Primary recommendation:** Planear en tres bloques. **(A)** Tareas del agente que dejan CI en verde en local y en la rama de fase: config.toml, uv.lock, ruff/mypy, eslint, íconos, health/yo/diagnóstico, migración de procrastinate, contraseña de `lucg_api` fuera de la migración, workflows con CLI v3 fijada y acciones actualizadas, tokens en el sitio, Playwright visual. **(B)** Pasos humanos guiados: organizaciones, transferir el repo, rama por defecto `dev`, proyectos de Supabase, Railway, Vercel y Sentry, DNS, secretos. **(C)** Cierre: el agente fusiona a `dev`, se verifica en dev, y el humano abre y fusiona `dev→main` y reúne la evidencia de prod.

### Pattern 1: Despliegue Railway de dos servicios desde Actions con SHA

**What:** Una imagen y dos servicios. La versión viaja en el archivo subido, porque `railway up` sube un archivo local y Railway no conoce el commit.

**When:** `deploy-dev.yml` / `deploy-prod.yml`.
```yaml
# Source: docs.railway.com/cli/up (flags --path-as-root, --service, --ci) [CITED]
- name: Desplegar API y worker
  env: { RAILWAY_TOKEN: "${{ secrets.RAILWAY_TOKEN }}" }   # token de PROYECTO, limitado al entorno (dev o prod)
  run: |
    npm i -g @railway/cli@5
    echo "${GITHUB_SHA}" > apps/api/VERSION
    railway up apps/api --path-as-root --service api --ci
    railway up apps/api --path-as-root --service worker --ci
```
```json
// apps/api/railway.api.json — en Railway › servicio api › Settings › Config file: /railway.api.json
// (con --path-as-root la raíz del archivo es apps/api) [ASSUMED A4: la ruta del config se resuelve contra la raíz subida]
{ "$schema": "https://railway.com/railway.schema.json",
  "build": { "builder": "DOCKERFILE", "dockerfilePath": "Dockerfile" },
  "deploy": { "healthcheckPath": "/api/v1/health", "healthcheckTimeout": 120,
              "restartPolicyType": "ON_FAILURE",
              "multiRegionConfig": { "us-east4-eqdc4a": { "numReplicas": 1 } } } }
// railway.worker.json: igual sin healthcheckPath y con
//   "startCommand": "procrastinate --app app.jobs.worker.app worker", "restartPolicyType": "ALWAYS"
```
Dockerfile: `COPY VERSION* ./`, y luego `CMD uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000} --proxy-headers --forwarded-allow-ips="*"` (forma shell para expandir `PORT`). `app/core/version.py` lee `VERSION` si existe y si no `APP_VERSION`. `/health` devuelve `version = sha[:7]` (lo que compara `deploy-dev.yml`) y Sentry usa `release = sha completo`, igual que `getsentry/action-release` con `github.sha`.

Opción descartada: autodeploy de Railway por GitHub. Pierde el orden "migrar → desplegar" que exige D-16. D-01 además manda conservar el enfoque de `deploy-dev.yml`.

### Pattern 2: Conexión a Supabase desde Railway
- Usar el **pooler compartido en modo sesión**: `postgresql+psycopg://lucg_api.<ref>:<pwd>@aws-<N>-us-east-1.pooler.supabase.com:5432/postgres?sslmode=require`. La conexión directa es **solo IPv6** en Free y el pooler compartido es IPv4. Con rol propio el usuario es `[ROLE].[PROJECT-REF]`. El host (`aws-[INDEX]`) **se copia del diálogo Connect**, porque no se puede deducir [CITED: supabase.com/docs/guides/database/connecting-to-postgres].
- El worker **requiere modo sesión o conexión directa**, porque procrastinate usa LISTEN/NOTIFY y el modo transacción (6543) no lo soporta [CITED: mismo doc].
- Pools pequeños. El pooler en modo sesión retiene una conexión de backend por cliente: SQLAlchemy `pool_size=3, max_overflow=2` y procrastinate con un pool pequeño. El tope del pooler de Free es ASSUMED A5.

### Pattern 3: Auth por JWKS + contexto por transacción + `/yo`
```python
# app/core/auth.py — solo algoritmos asimétricos. Supabase alojado firma con ES256/RS256 [CITED: supabase.com/docs/guides/auth/signing-keys]
ALGS = ["ES256", "RS256"]
claims = jwt.decode(token, key, algorithms=ALGS, audience=s.supabase_jwt_audience,
                    issuer=f"{str(s.supabase_url).rstrip('/')}/auth/v1")
```
```python
# app/api/v1/yo.py — prueba de D-12: el JWT es válido y set_contexto rige dentro de la transacción
@router.get("/yo")
def yo(p: Annotated[Principal, Depends(principal_actual)],
       s: Annotated[Session, Depends(sesion_dep)]) -> dict[str, object]:
    fila = s.execute(text("select current_user, app.org_tipo(), app.es_interno()")).one()
    return {"usuario": p.user_id, "roles": p.roles, "rol_db": fila[0], "org_tipo": fila[1], "interno": fila[2]}
```
`sesion_dep` envuelve `sesion_con_contexto(principal)` como dependencia generadora de FastAPI. Pruebas unitarias: generar una clave EC P-256 en el test, firmar tokens y sobrescribir `_jwks` o la dependencia, sin depender de GoTrue. Caminos que se prueban: token válido, `aud` incorrecto, firmado HS256 → 401, expirado, sin token. La lista de algoritmos de hoy, `["ES256","RS256","HS256"]`, es un vector de confusión de algoritmos y además el JWKS local trae también una clave `oct`. Ver Pitfall 6.

### Pattern 4: Job de prueba del worker (D-14)
```python
# app/jobs/worker.py [CITED: procrastinate docs: periodic, get_job_status_async]
@app.task(name="ping", retry=1)
def ping() -> str: return "pong"

@app.periodic(cron="*/5 * * * *")
@app.task(name="latido")
def latido(timestamp: int) -> None: ...   # deja huella en procrastinate_jobs; también genera actividad en la base (D-08)
```
API: `POST /api/v1/diagnostico/ping` (requiere rol `superadministrador`) → `await ping.defer_async()` → `{job_id}`. `GET /api/v1/diagnostico/jobs/{id}` → `await app.job_manager.get_job_status_async(id)`. La API abre la app de procrastinate en el `lifespan` (`async with worker_app.open_async()`). El e2e contra dev hace POST y consulta hasta `succeeded`. `/health` puede incluir `worker_ultimo_latido` (consulta a `procrastinate_jobs` con `task_name='latido' and status='succeeded'`); los nombres de columnas son ASSUMED A7 y se verifican contra el `schema --read`.

### Pattern 5: Migración del esquema de procrastinate
- `uv run procrastinate --app app.jobs.worker.app schema --read > supabase/migrations/<ts>_0002_procrastinate.sql`. `schema --apply` "no funciona si el esquema ya se aplicó", así que conviene que viva como migración versionada por pipeline [CITED: procrastinate cli.py].
- Al final de la migración: `grant usage on schema public to lucg_api; grant select, insert, update, delete on all tables in schema public to lucg_api` (solo las tablas `procrastinate_*`), y lo mismo para secuencias y `execute` de funciones `procrastinate_*`. Además **`revoke all … from anon, authenticated`** sobre esos objetos, porque `public` está expuesto por la Data API de Supabase (Pitfall 8).
- Fijar `procrastinate>=3.12,<3.13`. Cada subida de versión trae sus scripts de migración (`schema --migrations-path`), que se convierten en migraciones nuevas de Supabase.

### Pattern 7: Vercel con monorepo pnpm
- Sitio (proyecto `lucg` existente): Root Directory `apps/site`, framework Next.js. Web y driver (nuevos): Root Directory `apps/web` / `apps/driver`, framework Vite, salida `dist`. "Include files outside the root directory" viene activado por defecto en proyectos posteriores a 2020 [CITED: vercel.com/docs/monorepos/monorepo-faq].
- **pnpm 11:** el lockfile es `lockfileVersion: '9.0'` y Vercel usaría pnpm 9 o 10, que no entienden `allowBuilds` de `pnpm-workspace.yaml`. Hay que poner `ENABLE_EXPERIMENTAL_COREPACK=1` en los tres proyectos para que use `packageManager: pnpm@11.20.0` [CITED: vercel.com/docs/package-managers].
- Activar "Skip deployment" de proyectos no afectados (Root Directory). Funciona porque las dependencias `workspace:*` están declaradas, y por eso el sitio **debe** declarar `@lucg/ui` [CITED: vercel.com/docs/builds/configure-a-build].
- Dominio de rama: Settings › Domains › Edit › Connect to an environment = **Preview**, Git Branch = `dev` [CITED: vercel.com/docs/domains/working-with-domains/assign-domain-to-a-git-branch].
- Variables `VITE_*`: en Production (main) y en Preview **limitadas a la rama `dev`**. Los previews de PR usan las mismas de dev. `vite.config.ts` toma la versión de `VERCEL_GIT_COMMIT_SHA` (variable de sistema) [ASSUMED A9].
- `apps/web/vercel.json` y `apps/driver/vercel.json`: `{"rewrites":[{"source":"/(.*)","destination":"/index.html"}]}`. En driver además, cabecera `Cache-Control: no-cache` para `/sw.js` y `/manifest.webmanifest`.

### Pattern 9: PWA instalable sin red (D-13)
- Íconos: `pwa-assets-generator --preset minimal-2023 brand/LUCG_Logistics_logo.svg` genera 64, 192, 512, maskable-512 y apple-touch-180. En el manifest van entradas **separadas** `purpose: "any"` y `purpose: "maskable"`; no se usa `"any maskable"` combinado.
- `index.html`: `theme-color` `#011c52`, igual que el manifest (hoy dice `#0f172a`).
- Ya está bien: `registerType: "autoUpdate"`, `navigateFallback: "/index.html"`, precache por defecto de `**/*.{js,css,html}`. Se agrega `globPatterns` con `png,svg,webmanifest` y `navigator.storage.persist()` (ya existe).
- La prueba e2e: carga, espera `navigator.serviceWorker.ready` y que `navigator.serviceWorker.controller` no sea null (si hace falta recarga una vez), pide `manifest.webmanifest` y valida `name`, `start_url`, `display=standalone` y los íconos 192/512 con respuesta 200, luego `context.setOffline(true)` → `reload` → ve "Mi ruta de hoy" y "Sin red". Esto extiende `e2e/driver-offline.spec.ts`.

### Anti-Patterns to Avoid
- **`supabase db push` sin `--remote --yes` en CI:** en CLI v3 migra la base local del runner y el job sale verde sin tocar dev.
- **`setup-cli` con `version: latest`:** cambios de versión mayor sin aviso. Fijar la versión.
- **Contraseña de `lucg_api` en una migración de un repo público.**
- **Railway autodeploy + `migrate.yml` en paralelo:** se pierde el orden.
- **Exponer `/diagnostico/error` sin auth "porque es solo dev":** el mismo código va a prod (D-15 exige prod).
- **Poner `x-vercel-protection-bypass` en `extraHTTPHeaders` de todos los proyectos:** se filtraría en las peticiones a la API de Railway. Solo va en los proyectos que apuntan a Vercel, y se prefiere la cookie (`x-vercel-set-bypass-cookie`).

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Verificar JWT | Parser de JWKS propio | `PyJWKClient` (ya está) con algoritmos asimétricos y `issuer` | Rotación de `kid` y caché |
| Esquema de la cola | SQL escrito a mano | `procrastinate schema --read` como migración | Acoplado a la versión |

## Common Pitfalls

### Pitfall 1: Workflows que solo existen en `dev`
**What goes wrong:** `e2e-dev.yml` (`workflow_run`), el cron de salud (`schedule`) y `migrate.yml` (`workflow_dispatch`) no corren.
**Why:** GitHub: "This event will only trigger a workflow run if the workflow file exists on the default branch" vale para `schedule`, `workflow_run` y `workflow_dispatch` [CITED: docs.github.com events-that-trigger-workflows]. La rama por defecto es `main`, que todavía es el sitio viejo.
**How to avoid:** Paso humano: **cambiar la rama por defecto a `dev`**. La rama de producción de Vercel es otro ajuste y sigue en `main`. Como alternativa, en `deploy-dev.yml` se puede encadenar e2e como job y no por `workflow_run`. Se recomiendan las dos cosas: encadenar da orden determinista y no depende de la rama por defecto.
**Warning signs:** "Pruebas en dev" no aparece después de "Despliegue a dev". `cierre-fase.sh` paso 6 queda esperando un run viejo.

### Pitfall 2: Supabase CLI v3
**What goes wrong:** `db push` y `migration list` apuntan a la base local. Sin `--yes` falla con `HostedMutationConsentRequiredError`. Las claves de config eliminadas (`[inbucket]`) rompen `supabase start`.
**How to avoid:** `supabase link --project-ref "$REF"` y luego `supabase db push --yes --remote` y `supabase migration list --remote`. Poner `SUPABASE_ENV` en CI. Generar `config.toml` con v3 (usa `[local_smtp]`). Fijar `version: 3.4.0` y actualizar la CLI local, hoy 2.30.4 (`brew upgrade supabase`) [CITED: supabase.com/docs/guides/local-development/cli/migrating-to-v3].
**Warning signs:** El job de migraciones dura segundos y `migration list --remote` muestra 0001 sin aplicar.

### Pitfall 3: Deployment Protection de Vercel en los dominios dev
**What goes wrong:** `smoke.sh` (curl → 200), la espera de `deploy-dev.yml` y Playwright reciben 401 o la página de login de Vercel.
**Why:** Standard Protection "protects all domains except production domains", y `dev.`, `app-dev.` y `repartidor-dev.` son dominios de rama Preview [CITED: vercel.com/docs/deployment-protection].
**How to avoid:** Activar "Protection Bypass for Automation" en **cada uno** de los 3 proyectos (el secreto es por proyecto). Guardarlos como secretos `VERCEL_BYPASS_SITE|WEB|DRIVER` en los entornos de GitHub y mandarlos como cabecera `x-vercel-protection-bypass` (curl) o con cookie (Playwright) [CITED: vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation]. Quitar la protección de dev es una decisión de la fase diferida y no se toma aquí.
**Warning signs:** HTTP 401 con `_vercel_sso_nonce`.

### Pitfall 4: Cambiar el Root Directory del sitio en el orden equivocado
**What goes wrong:** Prod (`main`, sitio en la raíz) no puede reconstruirse con Root Directory `apps/site`.
**How to avoid:** Cambiar el Root Directory **ahora** (los previews de `dev` empiezan a compilar) y **no** redesplegar Production a mano hasta que `main` reciba el monorepo con el PR `dev→main`. El despliegue de prod que ya existe sigue sirviendo hasta entonces. Anotarlo en el runbook.

### Pitfall 5: Rol `lucg_api` con contraseña conocida en un repo público
**What goes wrong:** Entre `db push` y el `ALTER ROLE` manual, cualquiera puede entrar como `lucg_api.<ref>` / `lucg_api` por el pooler, que es público.
**How to avoid:** `0001_base` todavía no se aplica en ningún proyecto alojado, así que se puede editar el archivo. Crear el rol `login nobypassrls` **sin** `password` (sin contraseña la autenticación por contraseña falla) y poner `alter role lucg_api password 'lucg_api';` en `supabase/seed.sql`, que solo corre con `db reset` local o en CI. `db push` no aplica el seed salvo con `--include-seed` (ASSUMED A2). En dev y prod el humano corre `alter role lucg_api password '<generada>'` en el SQL editor (paso H-3) y la guarda solo en Railway.
**Warning signs:** `psql "postgresql://lucg_api.<ref>:lucg_api@…"` conecta.

### Pitfall 6: Confusión de algoritmos y JWKS local
**What goes wrong:** `algorithms=[…,"HS256"]` junto con un JWKS que trae una clave `oct` (la CLI local publica la clave simétrica si no hay `signing_keys_path`) [CITED: supabase/cli serve.ts vía Context7]. Un token HS256 firmado con un secreto que conoce un atacante (el de desarrollo es público) podría pasar.
**How to avoid:** `algorithms=["ES256","RS256"]`, validar `iss` y `aud`. En local la CLI firma con su `DEFAULT_SIGNING_KEY` asimétrica si no se configura `signing_keys_path` (CLI v3, ASSUMED para versiones viejas). Las pruebas unitarias usan su propia clave EC. Antes de configurar Railway, el humano verifica con `curl https://<ref>.supabase.co/auth/v1/.well-known/jwks.json` que hay claves asimétricas. Los proyectos nuevos usan claves asimétricas por defecto; la fecha exacta de ese cambio varía entre fuentes (mayo u octubre de 2025) y no afecta porque los proyectos se crean ahora.

### Pitfall 7: sentry-sdk 3 recoge más datos por defecto
**What goes wrong:** Cuerpos HTTP, info de usuario, consultas SQL y variables de los frames, que pueden incluir tokens o datos de destinatarios, llegan a Sentry. `send_default_pii` ya no existe [CITED: sentry-python MIGRATION_GUIDE].
**How to avoid:** `sentry_sdk.init(dsn, environment, release, traces_sample_rate=0.1, data_collection={...})` con la configuración restrictiva de la guía de migración (`user_info: False`, `http_bodies: []`, `database_query_data: False`, `stack_frame_variables: {"mode": "denylist"}`, denylist de cabeceras con `authorization`). Fijar `sentry-sdk[fastapi]>=3,<4`. En el navegador, `@sentry/react` 8 **sin** `sendDefaultPii`.

### Pitfall 8: Tablas de procrastinate en `public` expuestas por la Data API
**What goes wrong:** Supabase da grants a `anon` y `authenticated` sobre `public`, así que cualquiera con la clave publishable puede leer o encolar jobs por PostgREST (ASSUMED A1 sobre los grants por defecto actuales).
**How to avoid:** `revoke all on all tables in schema public from anon, authenticated` limitado a los objetos `procrastinate_*`, lo mismo en secuencias y funciones, y además `alter default privileges … revoke`. Si el asesor de seguridad marca "RLS disabled", habilitar RLS con una política `to lucg_api using (true)`. No usar RLS sin política, porque `lucg_api` es `nobypassrls` y el worker quedaría bloqueado.

### Pitfall 9: El puerto y el healthcheck en Railway
**What goes wrong:** Uvicorn escucha en 8000 y Railway enruta a `$PORT`, así que el healthcheck falla y el despliegue no se activa. Si `/health` devuelve 500 cuando la base falla, el error es poco claro.
**How to avoid:** `--port ${PORT:-8000}`. `/health` captura las excepciones de la base y devuelve **503** con `{"status":"degradado"}`. Railway solo enruta tráfico cuando ve 200, y eso protege de una `DATABASE_URL` mala.

### Pitfall 10: `wait-for-vercel-preview` con 3 proyectos
**What goes wrong:** La acción no tiene input de proyecto y puede devolver la URL del preview de `web` cuando se necesitaba la de `site` [CITED: README de la acción].
**How to avoid:** Usar `environment: "Preview – <nombre-proyecto>"` (Vercel nombra así los entornos de despliegue de GitHub cuando hay varios proyectos; ASSUMED A10, verificar en el primer PR) y `vercel_protection_bypass_header`. Si no funciona, consultar `GET https://api.vercel.com/v6/deployments?projectId=…&sha=$SHA` con un `VERCEL_TOKEN` de solo lectura.

### Pitfall 11: CORS para app-dev y los previews de PR
**What goes wrong:** El login funciona en Supabase pero la llamada a `/api/v1/yo` falla por CORS desde `https://app-dev.lucglogistics.com` o desde `*.vercel.app`.
**How to avoid:** `CORS_ORIGINS` en Railway dev = `https://app-dev.lucglogistics.com,https://repartidor-dev.lucglogistics.com`. Agregar `CORS_ORIGIN_REGEX` opcional, solo en dev, para `https://.*-lucg\.vercel\.app`. En prod la lista es exacta.

### Pitfall 12: Rutas absolutas en los archivos de GSD y en `settings.json`
**What goes wrong:** `"/opt/homebrew/bin/node"` en los hooks y `/Users/mateojaramillo/...` en agentes y comandos de GSD. Fallan en otra máquina y **publican el usuario local en un repo público**.
**How to avoid:** Cambiar a `node` en `settings.json` antes del commit. Ver Open Question 1 para los archivos de instalación.

### Pitfall 13: La guardia del agente no cubre los flags de v3
**What goes wrong:** El deny bloquea `supabase db reset --linked*`, pero en v3 el flag equivalente es `--remote`.
**How to avoid:** Agregar `Bash(supabase db reset --remote*)` al deny y la expresión correspondiente en `guardia-prod.sh`. `.claude/` tiene dueño en CODEOWNERS, así que este cambio lo revisa el humano.

### Pitfall 14: Supabase local en CI tarda y necesita el seed correcto
**How to avoid:** `supabase start -x studio,imgproxy,edge-runtime,logflare,vector,supavisor` (flag `--exclude`; la lista de nombres es ASSUMED en v3). Después `supabase db reset` aplica 0001, 0002 y el seed, que pone la contraseña local de `lucg_api`. `DATABASE_URL` local queda `lucg_api:lucg_api@127.0.0.1:54322`.

| V6 Cryptography | sí | TLS en todo (Railway/Vercel/Supabase `sslmode=require`). Nada de cripto hecha a mano |
| V7 Errors/Logging | sí | Sentry con `data_collection` restrictivo y sin PII en el navegador |
| V14 Config | sí | Secretos solo en GitHub Environments, Railway y Vercel. `.env*` en gitignore. Deny de lectura de `.env` para el agente |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Contraseña conocida de `lucg_api` en un repo público | Elevation | Rol sin contraseña en la migración. Contraseña local en el seed y la del alojado por SQL editor (H-3) |
| Confusión de algoritmo JWT (HS256 con clave `oct` en JWKS) | Spoofing | `algorithms=["ES256","RS256"]` + `iss` + `aud` |
| Tablas de procrastinate en `public` vía PostgREST | Tampering/DoS | `revoke` a anon y authenticated (+ RLS con política para `lucg_api` si el asesor lo pide) |
| Endpoint de error de prueba abierto | DoS (cuota de Sentry) | Auth + rol. En la PWA (sin login en 0.1) es un error **solo de cliente** en una ruta `/diagnostico` con confirmación, y no llama a la API |
| PII en Sentry (habeas data) | Info disclosure | `data_collection` restrictivo, `before_send` si hace falta, sin `sendDefaultPii` |
| Filtración del secreto de bypass de Vercel | Info disclosure | Secreto por proyecto, solo en entornos de GitHub, no en `extraHTTPHeaders` globales. Se regenera si se filtra |
| CORS abierto | Spoofing | Lista exacta en prod. Regex de previews solo en dev |
| Token de Railway con demasiado alcance | Elevation | Project token **por entorno** (dev token no despliega prod) en el entorno de GitHub que corresponde |
| Agente contra prod | Elevation | Hook `guardia-prod.sh` + deny. Agregar `supabase db reset --remote` (Pitfall 13). El entorno `prod` de GitHub tiene revisor requerido |
| Workflows de PR desde forks (repo público) | Info disclosure | `pull_request` (no `pull_request_target`). Los forks no reciben secretos |
