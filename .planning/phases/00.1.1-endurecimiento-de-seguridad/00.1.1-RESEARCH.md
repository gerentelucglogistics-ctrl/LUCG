## Summary

La fase es casi toda configuración y scripts sin dependencias nuevas: guardia en bash, compuerta de secretos en Python de biblioteca estándar, cambios en `playwright.config.ts`, `e2e/*.ts`, tres workflows y dos scripts, más ajustes en GitHub (bot colaborador, entornos de prod) y documentación (ADR-009, CLAUDE.md, SECURITY.md). Todo lo que necesita existe en el repo y en los runners.

La investigación encontró **cinco hechos que cambian el plan** frente a lo que supone CONTEXT.md:

1. **D-01 no se puede cumplir con un token fine-grained.** GitHub documenta que esos tokens no sirven "para contribuir a repositorios donde el usuario es colaborador". El repo es de una cuenta personal, así que el bot tiene que usar un **token classic** (`repo`, `workflow`, `read:org`, `gist`). Su alcance real queda limitado igual, porque el bot solo colabora en este repo. El desarrollador tiene que confirmar el cambio.
2. **Hoy cada despliegue a prod pide 4 aprobaciones, no una.** El run 46104076280 tiene 4 aprobaciones en `prod`, una por cada job que referencia el entorno (`aprobacion`, `migraciones/migrar`, `api`, `humo`). `deployment: false` no lo evita, porque los revisores siguen aplicando. Para cumplir el criterio 3, `deploy-prod.yml` debe tener **un solo job con `environment: prod`**.
3. **`e2e-preview` falla siempre.** Está en rojo en los PR #6, #7, #9 y #10 y en el último CI: la consola no muestra la versión de la API y el login no llega a `/consola`. El CORS de api-dev para previews sí responde bien. Con D-14, `fusionar-dev.sh` no fusionaría nada hasta repararlo, así que diagnosticarlo y arreglarlo es tarea obligatoria de la fase.
4. **"Por diseño" exige que el agente no tenga las credenciales de `jaras97`.** `gh` de esta máquina está autenticado como `jaras97` (revisor único de prod después de D-05) y git usa `osxkeychain`. Mientras el agente pueda leer ese token (`gh auth token -u jaras97`, `git credential fill`, `security`), puede aprobar prod con un script que la guardia no ve.
5. **El reporte HTML de Playwright guarda sus datos como zip en base64** dentro de `index.html` (`<template id="playwrightReportBase64">data:application/zip;base64,…`), y las trazas son zips dentro de `data/`. Un `grep` directo no encuentra nada. La compuerta tiene que decodificar y descomprimir de forma recursiva.

**Primary recommendation:** Ordenar la fase así: (0) reparar `e2e-preview` y hacer los ajustes de prod con el token de D-04 (D-18); (1) bot + aislamiento de credenciales; (2) Playwright sin secretos + compuerta; (3) guardia ampliada + pruebas en CI; (4) `deploy-prod.yml` con un solo job en `prod` + chequeo de `disable_signup`; (5) `fusionar-dev.sh` + ADR/CLAUDE.md/SECURITY.md. La prueba del criterio 2 es el PR de cierre de esta misma fase, que el bot fusiona con `fusionar-dev.sh`.

### Pattern 1: Bypass de Vercel por cookie, sin URL (D-11)
**Qué:** una petición con `APIRequestContext` manda `x-vercel-protection-bypass` y `x-vercel-set-bypass-cookie: true` como **cabeceras**. Vercel responde con `Set-Cookie` y redirección. Las cookies pasan al contexto del navegador. El secreto nunca toca una URL ni una acción de página.
**Por qué así:** la cabecera es el método recomendado por Vercel. La query solo está pensada para herramientas que no pueden mandar cabeceras [CITED: vercel.com/docs/deployment-protection/.../protection-bypass-automation]. `extraHTTPHeaders` en `use` mandaría la cabecera también a la API y rompería CORS (ya documentado en `bypass.ts`). Las peticiones del service worker de la PWA llevan la cookie.
```typescript
// e2e/bypass.ts — Fuente: playwright.dev/docs/api/class-apirequestcontext (storageState, addCookies)
import { expect, request as pwRequest, test as base } from "@playwright/test";
export const test = base.extend<{ bypassVercel: void }>({
  bypassVercel: [
    async ({ context }, use, testInfo) => {
      const nombre = testInfo.project.metadata?.bypassEnv as string | undefined;
      const secreto = nombre ? process.env[nombre] : undefined;
      const baseURL = testInfo.project.use.baseURL;
      if (secreto && baseURL) {
        const rc = await pwRequest.newContext({
          baseURL,
          extraHTTPHeaders: { "x-vercel-protection-bypass": secreto, "x-vercel-set-bypass-cookie": "true" },
        });
        await rc.get("/");                       // el título del paso es "GET /", sin cabeceras
        const { cookies } = await rc.storageState();
        await rc.dispose();
        await context.addCookies(cookies);       // la cookie es un token de Vercel, no el secreto
      }
      await use();
    },
    { auto: true },
  ],
});
export { expect };
```
Hay que comprobarlo en la primera corrida: después de `rc.get`, `cookies` no está vacío para el host del preview. Si Vercel no deja la cookie por esta vía, el respaldo es `context.route(u => u.host === host, r => r.continue({ headers: { ...r.request().headers(), "x-vercel-protection-bypass": secreto } }))`. Ese respaldo no cubre el service worker de `dev-driver` [ASSUMED].

### Pattern 2: Sesión por API + `storageState` (D-10)
**Qué:** un proyecto `setup` pide el token a `POST {SUPABASE_URL}/auth/v1/token?grant_type=password` (igual que `worker.spec.ts`) y escribe un `storageState` con la cookie de Vercel y la sesión de supabase-js en `localStorage`. No se abre ningún formulario.
```typescript
// e2e/auth.setup.ts — Fuente: playwright.dev/docs/auth ("Authenticate with API request")
import { test as setup, request as pwRequest } from "@playwright/test";
import fs from "node:fs";
export const ARCHIVO = "playwright/.auth/admin.json";
setup("sesión de administrador por API", async ({ request }, testInfo) => {
  const { E2E_USER_ADMIN: u, E2E_PASS_ADMIN: p, E2E_SUPABASE_URL: sb, E2E_SUPABASE_PUBLISHABLE_KEY: k } = process.env;
  setup.skip(!u || !p || !sb || !k, "faltan variables de e2e");
  const r = await request.post(`${sb}/auth/v1/token?grant_type=password`, { headers: { apikey: k! }, data: { email: u, password: p } });
  if (!r.ok()) throw new Error(`login por API: HTTP ${r.status()}`);      // nunca imprimir el cuerpo
  const sesion = await r.json();
  sesion.expires_at ??= Math.floor(Date.now() / 1000) + sesion.expires_in;
  const baseURL = testInfo.project.use.baseURL!;
  const clave = `sb-${new URL(sb!).hostname.split(".")[0]}-auth-token`;   // supabase-js 2.119.2
  const cookies = /* cookie de Vercel como en el Patrón 1, si hay bypassEnv */ [];
  fs.mkdirSync("playwright/.auth", { recursive: true });
  fs.writeFileSync(ARCHIVO, JSON.stringify({
    cookies,
    origins: [{ origin: new URL(baseURL).origin, localStorage: [{ name: clave, value: JSON.stringify(sesion) }] }],
  }), { mode: 0o600 });
});
```
Config: proyecto `setup` (`testMatch: /auth\.setup\.ts/`, `use: { baseURL: web, trace: "off" }`, `metadata: { bypassEnv: "VERCEL_BYPASS_WEB" }`). `preview`, `dev` y `local` llevan `dependencies: ["setup"]`. La prueba autenticada hace `test.use({ storageState: ARCHIVO })`, va directo a `/consola` y comprueba `yo-rol-db = lucg_api` y `yo-org-tipo = lucg`. `playwright/.auth/` va al `.gitignore` y queda fuera de `playwright-report/`. El formato de sesión (`access_token`, `refresh_token`, `expires_at`, `user`…) es el que guarda supabase-js v2 [ASSUMED: falta confirmarlo en la primera corrida con `yo-rol-db` visible].

### Pattern 3: Reportes solo en fallo, sin trazas (D-08)
```typescript
// playwright.config.ts

```
`trace: 'off'` es el valor por defecto documentado [CITED: playwright.dev/docs/api/class-testoptions#trace]. En los workflows:
```yaml
- name: Compuerta de secretos
  id: compuerta
  if: failure() && <condición actual del job>
  env: { E2E_USER_ADMIN: ..., E2E_PASS_ADMIN: ..., VERCEL_BYPASS_WEB: ..., VERCEL_BYPASS_DRIVER: ..., VERCEL_BYPASS_SITE: ... }

```
En `e2e-preview` (job con `continue-on-error: true`), `failure()` sigue valiendo dentro de los pasos del job.

### Pattern 4: Compuerta que entiende el formato real del reporte (D-09)
**Hecho verificado:** Playwright 1.65.1 escribe `<template id="playwrightReportBase64">data:application/zip;base64,…</template>` en `index.html` (`lib/runner/index.js`, `_writeReportData`). Las trazas y los recursos van en `playwright-report/data/` (zips y archivos sueltos).
**Algoritmo:**
1. Leer los valores desde `os.environ` para los nombres que empiezan con `E2E_USER_`, `E2E_PASS_`, `E2E_TOKEN_` y `VERCEL_BYPASS_`, ignorando los vacíos.
2. Por cada valor, generar variantes: crudo, `quote(v, safe='')`, `quote_plus(v)`, escape JSON (`json.dumps(v)[1:-1]`) y escape HTML (`html.escape`). Compararlas como bytes.
3. Recorrer los archivos. Si es zip, o si es el `<template>` base64, decodificar y entrar de forma **recursiva** (zips dentro de zips). Buscar las variantes en cada entrada.
4. Imprimir solo `ruta/entrada: <NOMBRE_DE_VARIABLE>`, nunca el valor. Con hallazgos: `shutil.rmtree(report)` y `exit 1`.
5. Si no hay ningún secreto definido, salir 0 con un aviso. No debe fallar en forks.

### Pattern 5: Guardia ampliada (D-06, D-07)

### Pattern 6: Registro cerrado verificable sin escribir (D-19)
- **Primario (solo lectura):** `curl -sf -H "apikey: $SUPABASE_PUBLISHABLE_KEY" "$SUPABASE_URL/auth/v1/settings" | jq -e '.disable_signup == true'`. El campo sale directo de `config.DisableSignup` [VERIFIED: GET a dev devolvió `disable_signup: True`; CITED: github.com/supabase/auth internal/api/settings.go].
- **Secundario (literal de D-19, sin efectos):** `POST /auth/v1/signup` con `{"email":"humo@example.invalid","password":""}`. GoTrue revisa `DisableSignup` **antes** de leer parámetros (→ 422 `signup_disabled`). Si el registro estuviera abierto, la validación rechaza la clave vacía antes de crear el usuario, así que la prueba no crea usuarios en ningún caso [CITED: supabase/auth internal/api/signup.go]. Esta sonda no se ejecutó en esta investigación (el clasificador del entorno bloqueó el POST).
- **Variables:** el entorno `prod` tiene `SUPABASE_URL` pero **no** `SUPABASE_PUBLISHABLE_KEY` [VERIFIED: `gh variable list --env prod`]. Agregarla es escribir en el entorno prod, así que va en la ventana de D-18 (antes de la guardia) o como paso humano. Alternativa: variable de repo `SUPABASE_PUBLISHABLE_KEY_PROD`, porque el valor es público.
- `smoke.sh`: con `ENTORNO=prod`, si faltan las variables el humo **falla** (no se salta en silencio). En dev se agrega en `e2e-dev.yml` (ya tiene `E2E_SUPABASE_*`).

### Pattern 7: Un solo job en `prod` (criterio 3)
**Hecho verificado:** cada job que referencia un entorno con revisores espera su propia aprobación (run 46104076280: 4 aprobaciones). `deployment: false` no lo evita: "Reviewers must approve" [CITED: docs.github.com/.../control-deployments].
**Diseño:** `deploy-prod.yml` con un job `desplegar` (`environment: prod`) que hace, en orden: aviso de confirmación → migración (los mismos pasos de `migrate.yml`; conviene extraerlos a una acción compuesta local `.github/actions/migrar-supabase` para no duplicarlos) → Railway → espera de versión → humo (incluido `disable_signup`) → release de Sentry. `migrate.yml` se queda para dev (`workflow_call` desde deploy-dev) y para `workflow_dispatch`. Si se despacha con `entorno=prod`, igual pide aprobación de `jaras97`.
**No usar** un entorno `prod-secretos` sin revisores para los jobs siguientes. Cualquier colaborador con escritura (el bot) podría despachar `migrate.yml` desde `main` contra ese entorno sin aprobación.

### Pattern 8: `fusionar-dev.sh` (D-13–D-15)
```bash
# Esqueleto; los mensajes van en español como el resto de scripts
set -euo pipefail
PR="${1:?uso: fusionar-dev.sh <PR>}"
BOT="${LUCG_BOT_LOGIN:?}"                       # o constante; no se deduce de gh api user
datos=$(gh pr view "$PR" --json baseRefName,author,headRefOid,isCrossRepository,state)
# base == dev, author.login == BOT, !isCrossRepository, state == OPEN   → si no, exit 1
# esperar: gh pr checks "$PR" --watch (tolerando rc=8 de pendientes), luego:
gh pr checks "$PR" --json name,bucket   # exigir api,web,e2e-preview,visual-sitio presentes y bucket ∈ {pass, skipping}
gh pr merge "$PR" --squash --delete-branch --match-head-commit "$SHA"   # SHA leído antes de evaluar los checks
```
- `--match-head-commit` existe en gh 2.101 [VERIFIED] y evita fusionar un push que llegó después de evaluar los checks.
- `e2e-preview` con `continue-on-error: true` reporta `bucket: fail` / `state: FAILURE` cuando falla [VERIFIED: PR #9]. El script lo trata como fallo (D-14).
- Si api-dev no responde, el job `e2e-preview` termina `pass` con los pasos saltados; el script lo acepta (es su "propia regla").
- Para PRs del bot con base `main`, `e2e-preview` no corre. No aplica, porque el script rechaza todo lo que no tenga base `dev`.

### Anti-Patterns to Avoid
- **`extraHTTPHeaders` global con el bypass:** manda el secreto a la API y a Supabase, rompe CORS y lo deja en las trazas.
- **`page.goto` con `?x-vercel-protection-bypass=`:** queda en el título del paso, en `test.trace` y en `*.network` (causa de T-0.1-19).
- **`fill()` con la clave real fuera de `local`:** el valor aparece en el título del paso (`Fill "<valor>"`).
- **`grep` directo sobre `playwright-report/`:** no ve nada, porque el contenido está en base64/zip.
- **Rutas absolutas `/Users/...` en `.claude/settings.json`:** rompen la compuerta de T-0.1-02. Lo que dependa de la máquina va en `.claude/settings.local.json` (gitignored).
- **Un entorno sin revisores para los secretos de prod:** abre una vía sin aprobación por `workflow_dispatch`.

## Don't Hand-Roll

| Problema | No construir | Usar | Por qué |
|----------|--------------|------|---------|
| Login del navegador en pruebas | Llenar el formulario y ocultar pasos | `storageState` con sesión por API | Patrón oficial de Playwright; el valor nunca pasa por una acción |
| Aprobar prod "una vez" | Lógica propia de aprobación (issues, comentarios) | Revisores del entorno en un solo job | Barrera de GitHub, auditada, con `can_admins_bypass:false` |
| Evitar fusionar un head que cambió | Releer el SHA en bucle | `gh pr merge --match-head-commit` | Es atómico en el servidor |
| Saber si el registro está cerrado | Llamar a la Management API con el token de prod | `GET /auth/v1/settings` con la clave publishable | Público, de solo lectura, sin secretos de prod |
| Auto-merge | Merge queue o auto-merge de GitHub | `fusionar-dev.sh` (D-15) | Decisión tomada; además `allow_auto_merge: false` en el repo [VERIFIED] |

**Key insight:** el hook es una lista de patrones sobre texto. La seguridad real viene de que **la identidad del agente no pueda** aprobar ni administrar prod. La guardia es la segunda capa y la que deja el registro.

## Common Pitfalls

### Pitfall 1: El agente sigue teniendo el token del revisor de prod
**Qué falla:** después de D-05, `jaras97` es el único revisor de prod, y su token está en el llavero de la misma cuenta de macOS. Un `python3 script.py` o `bash archivo.sh` que lo use para `POST pending_deployments` no lo ve la guardia, porque el hook solo inspecciona el texto del comando [CITED: code.claude.com/docs/en/permissions: "isn't a security boundary around the program"].
**Cómo evitarlo:** paso humano: `gh auth logout -u jaras97` en esta máquina (o moverlo a otro usuario de macOS), borrar la credencial de github.com de `osxkeychain` que use `jaras97`, y revisar/desactivar el plugin MCP de GitHub si tiene el token de `jaras97`. El desarrollador aprueba prod desde el navegador o GitHub Mobile. Si no quiere hacerlo, se registra como riesgo residual explícito y T-0.1-44 queda cerrada solo por la guardia (contra D-02 "por diseño").
**Señal:** `gh auth status` dentro de la sesión del agente muestra `jaras97`.

### Pitfall 2: Token fine-grained que no funciona
**Qué falla:** el bot crea un fine-grained con `gerentelucglogistics-ctrl` como owner y recibe 403/404. GitHub no admite fine-grained para colaboradores [CITED: docs.github.com/.../managing-your-personal-access-tokens, lista de limitaciones].
**Cómo evitarlo:** token classic con `repo`, `workflow`, `read:org`, `gist` y vencimiento (90 días recomendado, con recordatorio en STATE.md). Requiere confirmación del desarrollador porque cambia D-01.

### Pitfall 3: `fusionar-dev.sh` nunca fusiona porque `e2e-preview` está roja
**Qué falla:** `e2e-preview` falló en los PR #6, #7, #9 y #10 y en el último CI (run 46133871360). La consola no muestra la versión de la API (`api-version` sigue en "…") y el login no ve `yo-rol-db`. "Credenciales malas" pasa, así que Supabase sí responde. El preflight CORS de api-dev para un origen `lucg-web-…vercel.app` responde 200 con el origen permitido [VERIFIED].
**Hipótesis (sin confirmar):** `VITE_API_URL` del entorno Preview de Vercel en `lucg-web` falta o apunta a prod; o la URL de preview que devuelve `vercel-preview-url.sh` no es la del commit.
**Cómo evitarlo:** primera tarea (Wave 0): reproducir localmente con `BASE_URL_WEB=<preview>` y sin subir reportes; revisar las variables de Preview de `lucg-web` con la API de Vercel (`vercel-lucg`, sin imprimir valores). Si no se puede reparar, el desarrollador decide si D-14 se relaja temporalmente.

### Pitfall 4: Cuatro aprobaciones en vez de una
Ver Patrón 7. **Señal:** `gh api repos/o/r/actions/runs/<id>/approvals --jq length` > 1.

### Pitfall 5: Orden de la fase (D-18) y bloqueo por la propia guardia
**Qué falla:** si la guardia ampliada entra antes de ajustar `prod`/`Production`, el agente ya no puede hacerlo (bien) y todo pasa a ser paso humano. Si se ajusta después, se viola D-18.
**Cómo evitarlo:** plan 1 = ajustes de entornos de prod con `github-lucg` (lista exacta de llamadas en el plan, verificación con GET) **antes** de cualquier commit que cambie `guardia-prod.sh`. La guardia vive en el repo, pero aplica en cuanto el archivo cambia en el disco de la rama.

### Pitfall 6: Ventanas del reporte que la compuerta no cubre
- `error-context.md` (snapshot ARIA en fallo) muestra valores de los textbox. Solo pasa en `local`, donde se llena el formulario real.
- Las capturas PNG pueden mostrar texto. La consola muestra `yo.data.usuario`, que es el UUID, no el correo [VERIFIED: `yo.py`]. Riesgo bajo, la compuerta no lee imágenes. Se documenta.
- Los logs de Actions enmascaran el valor crudo de los secretos, pero **no** su forma URL-encoded. Con D-11 ya ninguna URL lleva secretos. Si un paso imprime variantes, agregar `::add-mask::`.

### Pitfall 7: `gh api` sin `-X` también escribe
`gh api ruta -f a=b` hace POST. La regla de "escritura" tiene que mirar los flags de campos, no solo `-X` [CITED: `gh help api`: "the default HTTP request method is GET normally and POST if any parameters were added"; ASSUMED: texto exacto].

### Pitfall 8: Vercel y commits del bot
La verificación de autor de Vercel aplica a repos **privados** de organizaciones; "no aplica a colaboradores en cuentas Git personales" [CITED: vercel.com/docs/git]. Este repo es público y personal, así que los commits del bot deberían desplegar. Hay reportes recientes en la comunidad de bloqueos en Hobby [LOW: community.vercel.com], así que se confirma con el primer PR del bot (es parte del criterio 2).

### Pitfall 9: La justificación de D-17 parte de un supuesto inexacto
Los PRs dev→main (#3, #8) los fusionó `gerentelucglogistics-ctrl` y los runs de deploy-prod los disparó esa cuenta; las 4 aprobaciones también las dio ella [VERIFIED: gh]. Con el revisor único `jaras97`, `prevent_self_review` **no** bloquearía al desarrollador mientras fusione con la cuenta LUCG. D-17 sigue siendo válida (deja libre fusionar con cualquiera de las dos cuentas), pero en SECURITY.md conviene escribir la justificación con este hecho. Tampoco cambia nada para el agente: el token `github-lucg` puede **disparar** deploy-prod (merge o dispatch, bloqueados por la guardia), pero no aprobarlo.

### Pitfall 10: `cierre-fase.sh` y `--delete-branch`
`gh pr merge --delete-branch` deja la copia local en `dev` (W-1 de 00.1-11). `fusionar-dev.sh` hereda ese comportamiento: después de fusionar hay que volver a una rama `fase/…` antes de escribir.

| Reporte HTML con archivos sueltos | Datos embebidos como zip base64 | Playwright actual (1.65.1 verificado) | La compuerta tiene que decodificar |

## Open Questions

1. **¿Token classic para el bot (en lugar del fine-grained de D-01)?** Lo que sabemos: fine-grained no funciona para colaboradores. Recomendación: classic `repo, workflow, read:org, gist`, 90 días. Plan B: GitHub App. **Lo confirma el desarrollador antes del plan del bot.**
2. **¿El desarrollador saca las credenciales de `jaras97` de la sesión del agente?** Sin eso, D-02 "por diseño" no se cumple (Pitfall 1). Recomendación: sí, y aprobar prod desde el navegador o el móvil.
3. **¿Por qué falla `e2e-preview`?** Hay que diagnosticarlo en Wave 0 (Pitfall 3).
4. **Ajustes de prod (D-18): ¿agente con `github-lucg` o humano?** Recomendación: el agente, en el primer plan, con la lista cerrada de llamadas (PUT `prod`, DELETE o PUT `Production`, variable `SUPABASE_PUBLISHABLE_KEY` en prod), verificación por GET y commit de la guardia justo después.
5. **¿Defensa en GitHub para `main` además de la guardia?** El bot (escritura) puede técnicamente fusionar PRs a `main` si los checks pasan; colaboradores de repo personal "pueden crear, fusionar y cerrar PRs" [CITED: docs.github.com permission-levels-for-a-personal-account-repository]. Opción: ruleset en `main` con "Restrict updates" y bypass solo para el rol admin, porque el desarrollador fusiona como `gerentelucglogistics-ctrl` [A5]. Fuera de las decisiones tomadas; el planificador lo propone o lo registra como residual.
6. **¿El bot puede escribir secretos y variables?** [A6] Después de crear el bot, se verifica con una llamada de solo lectura (`GET actions/secrets/public-key` con su token) y se documenta.

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Secreto en URL o paso de reporte público | Information disclosure | Cabecera + cookie; `storageState`; trazas apagadas; compuerta |
| Agente que se aprueba prod | Elevation | Identidad sin rol de revisor; credenciales del revisor fuera de su alcance |
| Admin que se salta la revisión | Elevation | `can_admins_bypass:false` |
| Evasión de la guardia por comillas, ruta absoluta, `gh api -f` o `curl` | Elevation | Delimitadores ampliados, detección de campos, reglas de `curl`; residual: scripts en disco |
| Despacho de workflow contra un entorno sin revisores | Elevation | Un solo entorno con secretos de prod, y con revisor |
| Fusión de un head distinto al revisado | Tampering | `--match-head-commit` |
